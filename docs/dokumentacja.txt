1. WYBÓR PLATFORMY CHMUROWEJ
---------------------------------------------------------

Wybraliśmy Amazon Web Services (AWS) z kilku powodów.
Po pierwsze, AWS Free Tier daje 750 godzin miesięcznie
na instancję EC2 t3.micro przez 12 miesięcy — to w zupełności
wystarczyło na potrzeby projektu. Po drugie, AWS jest
najpopularniejszym dostawcą chmury i znaleźliśmy dużo
materiałów pomocniczych przy konfiguracji. Po trzecie,
w razie potrzeby łatwo można rozbudować projekt o kolejne
usługi (np. RDS, S3) bez zmiany platformy.

Porównaliśmy też inne opcje:
- Google Cloud Free Tier — mniej czytelna konsola, gorsze
  materiały po polsku
- Azure for Students — wymaga weryfikacji uczelnianego maila,
  a nasz uczelniany mail sprawiał problemy przy rejestracji

Ostatecznie zdecydowaliśmy się na AWS.

Wykorzystane usługi w ramach Free Tier:
- EC2 t3.micro (Ubuntu 24.04 LTS) — serwer aplikacji
  750 h/miesiąc gratis przez 12 miesięcy
- EBS 8 GiB (dysk instancji) — w ramach 30 GB gratis

Ograniczenia na jakie trafiliśmy:
- t3.micro ma 1 GB RAM — wystarczające, ale npm install
  trwał dłużej niż lokalnie
- 15 GB ruchu wychodzącego miesięcznie — bez problemu
  dla projektu akademickiego

2. ARCHITEKTURA SYSTEMU
---------------------------------------------------------

Schemat (uproszczony):

  UŻYTKOWNIK (przeglądarka)
        |
        | HTTP port 80
        v
  +------------------------------+
  |   AWS EC2 t3.micro           |
  |   Ubuntu 24.04 LTS           |
  |   region: eu-north-1         |
  |   IP: 13.60.85.134           |
  |                              |
  |   [Nginx :80]                |
  |       | proxy_pass           |
  |       v                      |
  |   [Node.js/Express :3000]    |
  |       |                      |
  |       v                      |
  |   [SQLite - events.db]       |
  |                              |
  |   [PM2 - process manager]    |
  +------------------------------+
        |
        | SSH port 22
        v
  MY (terminal lokalny)

Opis poszczególnych elementów:

EC2 t3.micro (Ubuntu 24.04 LTS)
  Wirtualna maszyna Amazona w regionie eu-north-1 (Sztokholm).
  Wybraliśmy Sztokholm jako najbliższy region europejski.
  Security Group z otwartymi portami: 22 (SSH), 80 (HTTP).

Nginx
  Reverse proxy — przyjmuje ruch na porcie 80 i przekazuje
  go do aplikacji Node.js działającej na porcie 3000.
  Dzięki temu aplikacja nie musi działać jako root.

Node.js 20 LTS + Express.js
  Backend aplikacji, REST API:
    GET  /api/events                 lista wydarzeń
    GET  /api/events/:id             szczegóły
    POST /api/events                 dodaj wydarzenie
    POST /api/events/:id/register    rejestracja

SQLite (biblioteka better-sqlite3)
  Baza danych jako jeden plik events.db na dysku.
  Dwie tabele: events i registrations.
  Wybraliśmy SQLite żeby nie stawiać osobnego serwera bazy —
  dla skali tego projektu to w pełni wystarczające rozwiązanie.

PM2
  Zarządza procesem Node.js — restartuje go automatycznie
  gdy serwer się zrestartuje lub aplikacja crashnie.

Frontend
  Trzy strony HTML serwowane statycznie przez Express:
    index.html  — lista wydarzeń z kartami
    create.html — formularz tworzenia nowego wydarzenia
    event.html  — szczegóły + formularz rejestracji
  Stylowanie przez Bootstrap 5 ładowany z CDN (bez npm).

3. KONFIGURACJA I WDROŻENIE
---------------------------------------------------------

Zależności (package.json):
  express        4.18  — serwer HTTP i routing
  better-sqlite3  9.0  — obsługa bazy SQLite
  cors            2.8  — nagłówki CORS
  dotenv         16.0  — zmienne środowiskowe

Konfiguracja Nginx (/etc/nginx/sites-available/events-platform):

  server {
      listen 80;
      server_name _;
      location / {
          proxy_pass http://localhost:3000;
          proxy_set_header Host $host;
          proxy_set_header X-Real-IP $remote_addr;
      }
  }

Uruchomienie przez PM2:
  pm2 start server.js --name events-platform
  pm2 startup
  pm2 save

Kroki wdrożenia które wykonaliśmy:

1. Założyliśmy konto AWS na aws.amazon.com/free
2. Uruchomiliśmy instancję EC2:
   - AMI: Ubuntu Server 24.04 LTS
   - Typ: t3.micro (Free Tier eligible)
   - Region: eu-north-1 (Stockholm)
   - Security Group: SSH (22), HTTP (80)
   - Klucz SSH: wygenerowany przez AWS, pobrany jako .pem
3. Połączenie z serwerem:
   ssh -i ~/.ssh/events-platform-key.pem ubuntu@13.60.85.134
4. Pobranie kodu:
   git clone https://github.com/Loxingrgmws/events-platform.git
   cd events-platform
5. Uruchomienie skryptu deploy:
   chmod +x scripts/deploy.sh
   ./scripts/deploy.sh
6. Aplikacja dostępna pod: http://13.60.85.134

5. NAPOTKANE PROBLEMY I JAK JE ROZWIĄZALIŚMY
---------------------------------------------------------

Problem 1 — node_modules w repozytorium
  Przy pierwszym commicie przez GitHub Desktop nie mieliśmy
  pliku .gitignore, przez co folder node_modules (107 paczek)
  trafił na GitHub.
  Rozwiązanie: dodaliśmy .gitignore i usunęliśmy pliki
  poleceniem git rm --cached -r node_modules.

Problem 2 — Błąd autoryzacji przy git clone
  GitHub nie przyjmuje już hasła użytkownika dla operacji
  git przez HTTPS — wymaga Personal Access Token.
  Rozwiązanie: ustawiliśmy repozytorium jako publiczne,
  dzięki czemu git clone działa bez autoryzacji.

Problem 3 — Strona nie ładowała się po wdrożeniu
  Aplikacja działała na porcie 3000 i Nginx był uruchomiony,
  ale przeglądarka pokazywała pustą stronę.
  Okazało się, że Security Group na AWS miała otwarte tylko
  porty SSH (22) i HTTPS (443), a nie HTTP (80).
  Rozwiązanie: dodaliśmy regułę HTTP port 80 w ustawieniach
  Security Group w konsoli AWS.

Problem 4 — Zły typ instancji
  W specyfikacji projektu pisaliśmy o t2.micro, ale nowe konta
  AWS mają jako domyślny Free Tier t3.micro.
  Rozwiązanie: wybraliśmy t3.micro, który też jest Free Tier
  eligible — aplikacja działa bez zarzutu.
